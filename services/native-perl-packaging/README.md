# Complete Perl Debian package candidate

Prepare the published Perl 5.44.0-2 recipe and its complete binary package family before replacing the old Perl runtime in Debian runner images. The separate original-publisher profile in #359 already executed its complete supported harness and retains its platform skips/TODO outcomes. That original-source proof does not establish this Debian recipe or its installed packages.

All four source-package inputs and all 41 published patches are hash-pinned. The hosted SDK installs the official Debian keyring and requires a valid OpenPGP source signature and strong checksums through normal dpkg-source options before extraction. No signature, dependency, interpreter, compiler, configure-regeneration or root check is disabled. Source ddf63b6 passed these required gates and the normal complete package build in hosted run 40134337871; that dated build evidence does not prove installation or runtime behavior. Candidate binary packages are unsigned review artifacts.

The SDK runs as UID 10001 in a disposable, network-disabled, read-only-root container with no capabilities and bounded memory, CPU, process and temporary storage. Normal dpkg-buildpackage binary construction builds the complete published family, including static/shared/debug flavours and documentation. The recipe's supported CC/CPP/LD variables select GCC 16.2; each generated flavour config must confirm that version. Python 3.15.1, normal build-dependency checks, compatibility level 13 and the unmodified packaging tests remain in place. No stage1/nocheck/nodoc profile or package subset is selected.

Debian's existing recipe changes five original test files and sets PERL_BUILD_PACKAGING. Those published adaptations are recorded separately from the untouched publisher proof. Source helpers may only finish with the exact publisher or hash-bound published-recipe contents; no additional assertion, test exclusion or source patch is authored. Full original-case/platform acceptance is never inferred from the normal package build. Complete build logs and visible skip/TODO/expected-failure markers are retained.

Retain all generated packages, control/file lists, build metadata, input/keyring/tool identities, actual compiler configs and source/helper hash receipts on failure. Presence of partial packages does not imply qualification. No package is installed on the operator, server or application images. Installed dependency/reverse-dependency, CLI/module and native ABI compatibility, original installed-package behavior and strict whole-image advisory qualification remain required before integration. The complete Perl SDK package family must not be confused with the minimal perl-base family observed in the currently inspected runtime images.

Sources: [Debian source pool](https://deb.debian.org/debian/pool/main/p/perl/), [normal dpkg-source signature/checksum gates](https://manpages.debian.org/trixie/dpkg-dev/dpkg-source.1.en.html), [publisher releases](https://www.cpan.org/src/).


The initial f15b623 job stopped at the required signature gate: stable debian-keyring 2025.07.26 carries an older certificate for primary fingerprint 76A28E42C9811D91E88FBA5E2EC0FFB3B7301B1F whose expiry was December 2025. A fifth pinned input retrieves only that existing key's public certificate from Debian's official key service. Public-key armor is extracted from its HTML transport and its exact normalized bytes are SHA-256 bound. At 72b7ec1 GnuPG accepted the renewed certificate, but dpkg's default Sequoia backend still used the old vendor bundle and refused the signature. That backend does not load GnuPG's per-user trustedkeys.gpg.

SDK image preparation now merges the pinned renewal into a copy of the complete official public bundle, preserving its existing revocations and requiring exactly the same primary identity set and the same live signer fingerprint. Only the disposable SDK's standard vendor bundle is replaced; its original bundle is retained alongside it. The normal non-root package worker checks both bundle digests and retains the renewal receipt. The default dpkg backend is unchanged, and its required source-signature and strong-checksum gates must still pass under normal current-time, algorithm and revocation policy. No clock, expiry, signature or trust-model bypass is used, no different primary key is accepted, and operator/server trust stores are untouched. End-to-end source signature acceptance and complete package construction were independently verified at ddf63b6; installed-package acceptance remains a separate gate.


## Published installed-package profile

The follow-up profile first rebuilds the unchanged complete package family through the same non-root source/build gates. Only after that succeeds does a separate disposable testbed validate all candidate archive hashes and the original source identities. Normal APT simulation and installation require the complete family without removing existing testbed packages. ABI or reverse-dependency conflicts stop the profile; no force, ignored dependency, repository signature override or alternative installation root is used.

Package installation uses ordinary root package-manager privileges inside the disposable container. The unchanged package build still runs as UID 10001 with no capabilities. Debian autopkgtest runs every test declared by the original control file as source-build, including compression, historical database fixtures, Storable, native embedding, packaging metadata and configure verification. No test-name filter, overridden control, skipped restriction or insecure mode is selected. The exact twelve declared outcomes must all pass; original skips remain visible and do not establish full acceptance.

The installed testbed is network-disabled with bounded CPU, memory, processes and temporary filesystems. Only the reviewed public inputs and candidate outputs are mounted read-only, alongside a separate writable evidence directory. There is no Docker socket, host source tree, credential, operator database or application deployment. The manager has only the capabilities needed for ordinary file ownership and user changes; cases run as the normal user. Retain dependency diagnostics, package identities, complete autopkgtest results and hashes even on failure. Installed acceptance on this one amd64 testbed remains pending and will not establish every reverse dependency, platform or production image.

Interface: [Debian autopkgtest manual](https://manpages.debian.org/trixie/autopkgtest/autopkgtest.1.en.html). The source archive supplies the cases and control metadata; this profile adds orchestration and identity gates only.
