# Claimed Effect and Source-Head Safety Audit
Date: 2026-10-01. Source-only review of the shared working checkout.

## Verdict and Evidence Boundary
The new boundary is an exact-operation/version/live-claim prerequisite, not a latest-source fence. Its private scope is included in the managed final-effect digest. No production files were edited for this audit. No tests, builds, formatters, runtime processes, network, containers, or agents were started. Findings below are source-derived; concurrency schedules and PostgreSQL behavior were not exercised. Parent changes landed during inspection; this report includes the refreshed final-boundary namespace guards and the old-v1 receipt correction.

## Concrete Findings

### 1. P1: Runtime Lab HTTP requests use the configured owner's authority
The router constructs one Runtime Lab service using the configured module owner and broker: [routes.go:920](../backend/internal/router/routes.go):920. The routes require a nonempty authenticated subject and role permission, but do not compare that subject with the configured owner: [routes.go:1941](../backend/internal/router/routes.go):1941, [identity.go:63](../backend/internal/router/identity.go):63, [authz.go:15](../backend/internal/router/authz.go):15. SelfTest passes only context/runtime ID to the shared service: [handler.go:62](../backend/internal/runtimelab/handler.go):62. The operation and claim use s.owner/s.space: [service.go:192](../backend/internal/runtimelab/service.go):192, [service.go:216](../backend/internal/runtimelab/service.go):216.

Consequence: another authenticated subject with execute permission can request an operation and filesystem self-test under the configured owner. Read/attempt endpoints similarly use the shared owner's service state. The new scope checks agree with that configured identity, so they do not fix this confused-deputy path. Exposure assumes more than one accepted subject; no deployment or token issuance was inspected. Minimum fix: reject a subject mismatch for an explicitly single-operator lab, or build genuinely caller-scoped service/broker/attempt storage. Do not merely overwrite the operation owner while retaining another owner's broker.

### 2. P1: Lock-held authorization has a context-free database dependency
The boundary holds a database transaction across the callback: [claimed_effect_boundary.go:172](../backend/internal/operations/claimed_effect_boundary.go):172, [claimed_effect_boundary.go:207](../backend/internal/operations/claimed_effect_boundary.go):207. That callback issues authorization and later resolves/re-authorizes/consumes it using separate service repository calls: [executionauth_bridge.go:99](../backend/internal/executionbroker/executionauth_bridge.go):99, [executionauth_bridge.go:155](../backend/internal/executionbroker/executionauth_bridge.go):155. Consumption opens its own transaction: [repository_postgres.go:220](../backend/internal/executionauth/repository_postgres.go):220.

Most calls carry context, but Constitution evaluation does not: [executionauth/service.go:230](../backend/internal/executionauth/service.go):230, [constitution_adapter.go:31](../backend/internal/executionauth/constitution_adapter.go):31. It reaches a query without WithContext: [frameworkregistry/service.go:687](../backend/internal/frameworkregistry/service.go):687, [frameworkregistry/repository.go:188](../backend/internal/frameworkregistry/repository.go):188. Default repositories share the cached database: [infra/database.go:43](../backend/internal/infra/database.go):43.

Consequence: with one available pool connection occupied by the outer transaction, authorization needs another connection. Contextual calls can time out; the Constitution query itself is not bounded by the callback context. A stalled query/callback can exceed the advertised five-second cooperative budget. Cancellation may release the outer SQL transaction, so this is not proof that SQL row locks remain held indefinitely. Current source does not establish a spare-connection reserve or distinct bounded policy pool. Minimum next step: propagate context through every final-boundary policy lookup, cap admission against actual pool capacity, and verify the small-pool schedule. Do not solve pool pressure by dropping the authoritative lock before authorization/effect. No current operation/auth reverse-row-lock cycle was proved.

### 3. P1: Live mode and block-rule changes are not checked at the final effect
Managed worker/manual/self-test policy checks occur before the running transition and broker authorization: [worker.go:450](../backend/internal/background/worker.go):450, [phase2/handler.go:371](../backend/internal/phase2/handler.go):371, [runtimelab/service.go:226](../backend/internal/runtimelab/service.go):226. The final bridge reconstructs a fixed low-risk/autonomy-8 request; it does not consult Phase 2 mode or block rules: [executionauth_bridge.go:278](../backend/internal/executionbroker/executionauth_bridge.go):278. Executionauth separately checks its persisted emergency-stop evaluator: [executionauth/service.go:166](../backend/internal/executionauth/service.go):166.

Consequence: a change to observe/draft mode or block-similar after the upstream check, including while waiting on the DB, can still be followed by the file effect. Operation/claim locks do not lock these independent controls. Direct local-worker execution also omits the upstream policy entirely: [safe_worker_runtime.go:52](../backend/internal/runtimelab/safe_worker_runtime.go):52, [local_safe_worker.go:136](../backend/internal/executionbroker/local_safe_worker.go):136. No arbitrary-payload Runtime Lab HTTP execute route was found; that direct route is an in-process API, whereas HTTP self-test uses the managed ledger path. Minimum contract: explicitly define which controls gate ad-hoc versus managed effects and evaluate the required controls at the final boundary. Emergency stop is not being claimed absent.

### 4. P2: Detached context can defeat the original scope deadline while callback remains active
CurrentSafeEffectScope tests ctx.Err on the supplied context plus state.active: [claimed_effect_boundary.go:44](../backend/internal/operations/claimed_effect_boundary.go):44. The original callback deadline is not retained in activeSafeEffect. Scope is deactivated on return: [claimed_effect_boundary.go:107](../backend/internal/operations/claimed_effect_boundary.go):107, [claimed_effect_boundary.go:115](../backend/internal/operations/claimed_effect_boundary.go):115.

A callback that passes context.WithoutCancel(effectCtx) to a downstream broker can therefore preserve active scope after the original deadline until callback return, even if the outer SQL transaction is being rolled back. The landed managed callback passes effectCtx unchanged: [background/execute.go:146](../backend/internal/background/execute.go):146, so this is an API-hardening gap, not a demonstrated route exploit. Minimum fix: activeSafeEffect must also consult the original authority context/deadline. Keep callback execution synchronous; never launch an effect and return while it continues. After callback return, retained contexts and copied scope cannot independently reactivate private authority.

### 5. P2: Managed artifact naming has only 32 bits of operation identity
safePayload uses the first eight UUID characters: [worker.go:560](../backend/internal/background/worker.go):560. CreateExclusiveFile refuses an existing target: [local_safe_worker.go:248](../backend/internal/executionbroker/local_safe_worker.go):248.

Two different operations sharing that prefix contend for the same filename despite having different markers/digests. The second attempt can consume authorization then fail creation, entering uncertainty rather than completing its own task. This is an availability/reconciliation defect, not an overwrite: exclusive creation is preserved. Prefer the full operation UUID in the managed filename; do not repair by overwriting or deleting the first artifact.

## Lock, Cancellation and Replay Limits
The callback is cooperatively timed, not a hard syscall deadline. Write, Sync, root creation, and verification perform synchronous filesystem operations: [local_safe_worker.go:235](../backend/internal/executionbroker/local_safe_worker.go):235, [local_safe_worker.go:282](../backend/internal/executionbroker/local_safe_worker.go):282. Context cancellation can roll back the SQL transaction while an already-entered filesystem call remains in progress; there is no atomic DB-lock-to-filesystem handoff. Preserve uncertainty, prohibit replay, and do not claim that cancellation undoes a file effect or proves locks remained held through syscall completion.

Heartbeat renewal takes the claim row alone and can wait behind the boundary: [execution_claim.go:252](../backend/internal/operations/execution_claim.go):252, [worker.go:291](../backend/internal/background/worker.go):291. This is not a demonstrated lock inversion because renewal does not then acquire the operation row. Callback code must not reenter operation repositories; the memory implementation holds its global mutex, and DB reentry can self-wait. Recovery currently locks operation before claim, consistent with transition/release.

A consumed receipt rejects reuse: [executionauth/repository_postgres.go:393](../backend/internal/executionauth/repository_postgres.go):393. But a different claim/version changes the managed digest and can mint a different receipt. The locked scope is not a one-shot attempt token, and validateSafeEffectSnapshot does not independently validate the durable execution intent or enforce one exact payload per callback. Current background code supplies one synchronous payload and checks prior uncertainty. Do not broaden callbacks/direct APIs into arbitrary or repeated effects based solely on this scope. General Save/Update can rewrite WorldModelStateJSON; uncertainty needs its own durable invariant before it becomes cross-entry replay authority.

## Minimum Durable Source-Head Contract
Known remaining race, outside the exact-operation fence: intake can accept revision B as a different operation while revision A is running, because creation does not acquire A's row/claim lock. Claim selection has no cross-revision head predicate. A remains eligible for an exact-op callback even though B has been accepted. This is the specific serialization problem the following contract must close, not an allegation that the current parent change already claims to close it.

1. One unique tenant-scoped head per canonical source identity: owner, workspace, typed provider/account/external tuple, validated identity digest. Store current opaque revision, monotonically increasing accepted-observation generation, authoritative source/config epoch or cursor, and tombstone/invalid/reconciliation state. Never infer from URI or arrival timestamps. Current revision hashes are semantic content digests, not ordering tokens: [feed.go:130](../backend/internal/accountfeed/feed.go):130.
2. Establish who may publish a head and its ordering. Item-level provider/account overrides currently affect identity ([feed.go:112](../backend/internal/accountfeed/feed.go):112); owner-scoped background readers also alter account labels ([phase2/module.go:419](../backend/internal/phase2/module.go):419). Reconcile canonical identity across these intake paths and bind allowed source namespace/config in server authority. An old fetch finishing last must not supersede a newer accepted observation. For unordered file snapshots, serialize acquisition/acceptance per source or explicitly require reconciliation; content hashes and SourceReceivedAt do not prove latestness.
3. Global order: source head, operation, execution claim, then bounded authorization resources. Create/lock a missing head atomically with uniqueness or a tenant-scoped advisory key. Both intake publication and final effect must take the same head lock. Rework ClaimNext's operation-first selection before adding head checks; do not append a head lock after its current operation lock. Sort keys for multi-head/batch operations.
4. Final boundary, while holding head plus operation/claim locks, requires exact head generation/revision/config epoch, safe head state, operation identity/version/status, live owner/generation/lease, exact durable attempt/effect, and current required controls. Put that generation and source authority epoch in the server-issued final-effect digest. Reject absent/corrupt/changed head with no broker dispatch or partial success. Source-less self-tests need an explicit separate class, not automatic legacy acceptance.
5. Durable replay record keyed by semantic effect/authorized attempt, not just replaceable operation version or worker claim. Track reserved/consumed/started/verified/uncertain/reconciled states with append-only evidence. A new claim, version, authorization receipt, dedupe row after archive, or A-to-B-to-A source recurrence must not erase previous consumption or uncertainty. A higher observation generation is essential for recurrence.
6. Commit intent before dispatch and preserve durable consumption across outer transaction rollback. Moving consumption into the operation-lock transaction to save a pool connection would be unsafe if a file effect happens and cancellation then rolls back the only consumption record. Use a deliberately designed durable journal/authorization reservation protocol; distinguish proven before-effect refusal from after-consumption/partial/unknown outcomes. Do not claim exactly-once external effect from a transaction surrounding nontransactional I/O.
7. Retain source identity and identified revision immutability on every writer; restrict reconciliation to an explicit reviewed path. Current migration guards updates but deliberately do not recompute digests or create source-head authority: [0111 up:15](../backend/migrations/pre/0111_operation_source_identity.up.sql):15, [0111 up:50](../backend/migrations/pre/0111_operation_source_identity.up.sql):50.
8. State the guarantee narrowly: an effect is serialized against the latest *accepted durable observation*. A provider or local file changing without an authoritative accepted observation is not covered. Revocation/loss of the lock authority during already-entered I/O remains an uncertain outcome, not absence.
